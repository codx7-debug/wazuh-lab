## What I Built

This project is an **isolated Security Operations Center (SOC) laboratory** designed to understand the complete security telemetry pipeline—not merely to install Wazuh, but to trace how a raw security event travels from an endpoint or network sensor through collection, processing, decoding, rule evaluation, alerting, indexing, and finally visualization.

**Central Thesis:** *"Security Event → Collection → Processing → Detection → Alert → Indexing → Investigation"*

Through three hands-on detection scenarios, this lab demonstrates how telemetry becomes actionable intelligence in a modern SIEM environment.

### Event vs. Alert vs. Incident

It is critical to distinguish these three concepts:
Event
↓
Rule Match
↓
Alert
↓
Investigation
↓
Potential Incident
plain

| Stage | Definition |
|-------|------------|
| **Event** | Raw telemetry generated by a system or sensor (e.g., a Windows log entry, a Snort packet capture) |
| **Alert** | An event that matched detection logic (a Wazuh rule or Snort signature) |
| **Incident** | A confirmed security matter requiring response, determined through investigation of one or more alerts |

## Core Concepts

| Component | Role in the Pipeline |
|-----------|-------------------|
| **Wazuh Agent** | Collects configured telemetry and log sources from the endpoint, then securely forwards events to the Wazuh Manager. |
| **Wazuh Manager** | Receives incoming events, orchestrates pre-decoding, decoding, and rule evaluation. |
| **Pre-Decoding** | Identifies basic structure and context from the incoming raw log (e.g., timestamp, hostname, program name). |
| **Decoder** | Interprets a specific log format and extracts meaningful key-value fields from unstructured text. |
| **Rule** | Evaluates structured events against detection logic to determine if they represent suspicious or security-relevant activity. |
| **Alert** | The output of an event successfully matching a detection rule. |
| **Filebeat** | Lightweight data shipper that forwards Wazuh alert data from `alerts.json` to the Wazuh Indexer. |
| **Wazuh Indexer** | Stores and indexes alert data for high-performance search and retrieval. |
| **Wazuh Dashboard** | Provides visualization, querying, and investigation capabilities for analysts. |

### Decoder vs. Rule

| | Decoder | Rule |
|--|---------|------|
| **Question** | *"What information is contained in this event?"* | *"Does this event represent suspicious activity?"* |
| **Function** | Parses and extracts fields | Evaluates logic and generates alerts |
| **Config Location** | `/var/ossec/etc/decoders/` | `/var/ossec/ruleset/rules/` |

Troubleshooting Methodology
One of the most valuable skills developed in this project was layer-by-layer pipeline troubleshooting. When an expected alert does not appear in the dashboard, the following methodology isolates the failure point:
Table
Step	Question	Verification Target
1	Did the activity happen?	Confirm the action was executed (e.g., ping sent, failed login attempted)
2	Did the network/system receive it?	Verify with tcpdump or system logs
3	Did the security sensor see it?	Confirm Snort/Wazuh Agent is monitoring the correct interface/log
4	Did the sensor generate an event?	Check sensor logs (e.g., Windows Event Log, Snort capture)
5	Where did the sensor write the event?	Verify the actual configured output path
6	Can Wazuh read the log?	Check file permissions and Wazuh ossec.log
7	Did pre-decoding process it?	Review /var/ossec/logs/archives/archives.json
8	Did the decoder match?	Test with wazuh-logtest
9	Did a Wazuh rule match?	Review rule logic and decoder output
10	Was an alert generated?	Check /var/ossec/logs/alerts/alerts.json
11	Was it indexed?	Verify Filebeat and Indexer connectivity
12	Can the Dashboard display it?	Confirm index patterns and time range
Key Troubleshooting Lesson
"Always verify the actual log output configured by the security sensor before troubleshooting SIEM ingestion."
The Problem: I initially monitored /var/log/snort/alert for new Snort detections, but the active configuration was writing fast alerts to /var/log/snort/snort.alert.fast via output alert_fast: snort.alert.fast.
The Symptom: The alert file had an old timestamp, leading me to believe Snort was not detecting traffic—when in fact Snort was working correctly and writing to a different file.
The Resolution: Verified the active snort.conf output configuration, then pointed Wazuh log collection to the correct path.
Key Lessons Learned
Telemetry Pipeline Literacy: Understanding the difference between an event, a decoded event, and an alert is fundamental to SIEM engineering.
Sensor Configuration Ground Truth: The configuration file is the source of truth. Assumptions about default paths or behaviors lead to wasted troubleshooting time.
Decoder-Rule Separation: Decoders answer "what is this?"; rules answer "is this bad?". Keeping these concerns separate makes detection logic maintainable.
Layered Verification: Working through the pipeline step-by-step (network → sensor → log → SIEM → index → dashboard) transforms vague "it's not working" into precise diagnostic steps.
Built-in Capabilities: Before building custom solutions, investigate what the platform already provides (e.g., Wazuh's built-in Snort decoder).
